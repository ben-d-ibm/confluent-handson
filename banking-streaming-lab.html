Banking Real-Time Loan Decisions with Confluent

Construcción de una arquitectura de streaming end-to-end con Infrastructure as Code.

El cambio de enfoque de este laboratorio

En el laboratorio anterior exploraste las capacidades de Confluent Cloud interactuando con su interfaz gráfica (UI). En este segundo laboratorio cambiamos radicalmente de método: en lugar de crear componentes uno a uno desde la consola web, desplegaremos una arquitectura completa, gobernada y lista para producción utilizando Infrastructure as Code (IaC) y automatización.

«De crear recursos haciendo clics a desplegar una arquitectura de streaming reproducible.»

2. ¿Qué vamos a construir?

Resolveremos un caso financiero real: la evaluación y decisión automática de solicitudes de préstamo bancario en tiempo real.

Cuando un cliente solicita un crédito a través del canal digital, el sistema bancario necesita contrastar inmediatamente la solicitud con su perfil financiero y su historial crediticio:

  • Solicitud en curso: Importe solicitado, plazo en meses y finalidad del crédito.
  • Perfil maestro del cliente: Ingresos mensuales, nivel de endeudamiento actual, años de antigüedad laboral y segmento de cliente.
  • Comportamiento histórico de pagos: Registro acumulado de cuotas pagadas a tiempo, retrasos e impagos históricos (defaults).

El motor de streaming correlaciona estos flujos de eventos mediante temporal joins en Apache Flink y ejecuta el modelo de scoring RULES_V1 (puntuación de 0 a 100 puntos) para emitir una decisión instantánea:

APPROVED (Aprobado, si la puntuación es ≥ 60 y no registra impagos) o REJECTED (Rechazado, detallando los motivos exactos del rechazo).

Dimensión de Riesgo Cálculo / Métrica Ponderación (Máx. 100 pts)
Ratio Deuda/Ingresos (DTI) (deuda_mensual + cuota) / ingresos DTI ≤ 30%: 40 pts • ≤ 40%: 25 pts • ≤ 50%: 10 pts • > 50%: 0 pts
Historial de Pagos Impagos y retrasos acumulados Con impagos: 0 pts • 0 retrasos: 30 pts • ≤ 2 retrasos: 20 pts • > 2 retrasos: 8 pts
Estabilidad Laboral Años en el empleo actual ≥ 5 años: 15 pts • ≥ 3 años: 10 pts • ≥ 1 año: 5 pts • < 1 año: 0 pts
Importe vs Ingresos Anuales importe / (ingresos * 12) ≤ 50% anual: 15 pts • ≤ 100%: 8 pts • > 100%: 0 pts

Rol de cada componente

  • PostgreSQL 18: Base de datos relacional local que custodia los datos maestros de clientes y registros de pagos, configurada con REPLICA IDENTITY FULL.
  • Kafka Connect + Debezium: Conector CDC que lee los logs de replicación de PostgreSQL y emite eventos de cambio hacia Confluent Cloud con esquemas Avro.
  • Confluent Cloud: Clúster Kafka gestionado y Schema Registry que gobiernan los contratos de datos y garantizan almacenamiento escalable y seguro.
  • Flink SQL Compute Pool: Motor de procesamiento en streaming que ejecuta agregaciones continuas de estadísticas e invoca temporal joins para calcular el scoring al milisegundo.
  • Frontend de Solicitudes (Puerto 8080): Aplicación Express + React para registrar solicitudes de crédito manuales y publicarlas en formato Avro.
  • Dashboard de Decisiones (Puerto 8081): Cuadro de mando operacional en tiempo real que consume el tópico de decisiones y actualiza KPIs y gráficos en vivo.

4. Infrastructure as Code (IaC)

En este laboratorio, toda la topología se construye de manera automatizada y determinista mediante código:

make up
   │
   ├── cloud-up  ──> Terraform (terraform/)
   │                   ├── Confluent Environment & Kafka Cluster
   │                   ├── Schema Registry & Esquemas Avro
   │                   ├── Tópicos (loan-requests, customers, payment_history)
   │                   ├── Service Accounts, Role Bindings y ACLs de mínimo privilegio
   │                   ├── Flink Compute Pool
   │                   └── Salida: .env.runtime
   │
   ├── local-up  ──> Compose (compose/compose.yaml)
   │                   ├── PostgreSQL (esquema + seed determinista)
   │                   ├── Kafka Connect (registro del conector Debezium CDC)
   │                   ├── Frontend de Solicitudes (:8080)
   │                   └── Dashboard de Decisiones (:8081)
   │
   └── flink-up  ──> Terraform (terraform-flink/)
                       ├── Declaración de Claves Primarias CDC
                       ├── DDL & DML: customer_payment_stats
                       └── DDL & DML: loan-decisions (motor de scoring)
¿Por qué utilizar IaC en arquitecturas de streaming?
  • Reproducibilidad: Permite recrear el entorno completo en cualquier región o cuenta cloud sin desviaciones manuales.
  • Control de versiones: Toda la configuración de tópicos, umbrales de scoring, esquemas y ACLs reside en Git.
  • Seguridad por diseño: Cada microservicio recibe credenciales únicas y permisos estrictamente acotados mediante ACLs gestionadas por Terraform.
  • Limpieza absoluta: Se elimina todo el entorno con un único comando (make destroy), evitando costes residuales.

Utilizá Homebrew en la terminal de macOS para instalar las dependencias necesarias:

Terminal macOS

brew install terraform make jq curl openssl

8. Configurar credenciales

El asset incluye un script de inicialización que genera de forma segura tu archivo .env con contraseñas aleatorias para PostgreSQL y permisos restrictivos (chmod 600):

Terminal
make init

A continuación, abrí el archivo .env con tu editor de texto y completá tus credenciales de Confluent Cloud:

Archivo .env
# --- Confluent Cloud (OBLIGATORIO) -------------------------------------------
# Cloud API key (NO es una API key de clúster). Créala en:
#   Confluent Cloud > menú superior derecha > API keys > Add API key > Cloud resource management
CONFLUENT_CLOUD_API_KEY="TU_API_KEY_AQUI"
CONFLUENT_CLOUD_API_SECRET="TU_API_SECRET_AQUI"

# Región de AWS donde se despliega todo (clúster Kafka + Flink).
CLOUD_REGION="us-east-1"

# Prefijo para nombrar los recursos creados en Confluent Cloud.
PROJECT_NAME="banking-streaming"

# Capacidad máxima del pool de Flink (CFU).
FLINK_MAX_CFU=5

# --- Entorno local ------------------------------------------------------------
CONTAINER_RUNTIME="auto"
POSTGRES_PORT=5432
CONNECT_PORT=8083

# Generadas automáticamente por make init:
POSTGRES_PASSWORD="[generada-automáticamente]"
CDC_PASSWORD="[generada-automáticamente]"
Diferencia entre .env y .env.runtime

.env contiene tus variables de entrada (credenciales de Cloud, región, puertos).
.env.runtime es generado automáticamente por Terraform durante el despliegue con los endpoints del clúster y las API keys específicas de cada servicio. Nunca debés editar .env.runtime a mano.

10. Desplegar todo

Este es el comando principal del laboratorio. Ejecuta de forma secuencial y coordinada toda la infraestructura cloud, los contenedores locales, la captura CDC y Flink SQL:

Terminal
make up

Secuencia de ejecución de make up

  1. cloud-up (~45-60 s): Terraform crea el entorno en Confluent Cloud, el clúster Kafka, Schema Registry, los tópicos, las Service Accounts, ACLs y el Compute Pool de Flink. Luego genera el archivo .env.runtime.
  2. local-up (~20-30 s): Compose compila y levanta los contenedores (postgres, connect, frontend-requests en el puerto 8080 y frontend-dashboard en el puerto 8081). Se registra el conector Debezium y se verifica que esté en estado RUNNING.
  3. flink-up (~15-20 s): Se definen las Primary Keys de las tablas CDC y se aplican las sentencias persistentes de Flink SQL (agregación de estadísticas y scoring de decisiones).
Tiempo total estimado

El despliegue completo toma habitualmente entre 1 y 2 minutos dependiendo de la latencia de red y aprovisionamiento en la nube.

12. Abrir las aplicaciones

Abrí dos pestañas en tu navegador para interactuar con la plataforma:

  • UI de Solicitudes de Préstamo: http://127.0.0.1:8080
  • Dashboard Operacional en Tiempo Real: http://127.0.0.1:8081
Separación de responsabilidades y latencia de decisión

UI de Solicitudes (:8080): Su función es exclusivamente validar el formulario y confirmar la publicación del evento en Kafka respondiendo 202 Accepted. No calcula ni muestra la decisión del crédito.

Procesamiento en Flink: Flink procesa la solicitud mediante un temporal join contra el perfil del cliente y estadísticas de pago. En las pruebas del asset, la decisión se emite habitualmente en 5 a 10 segundos.

Optimización de particiones inactivas: Esta rapidez se logra configurando sql.tables.scan.idle-timeout = '5 s' en la sentencia dml-loan-decisions, lo que evita que las particiones sin tráfico detengan el avance del watermark del join.

Dashboard (:8081): Consume las decisiones desde el tópico loan-decisions y actualiza métricas y gráficos en vivo.

17. ¿Qué acaba de ocurrir?

Repasemos la secuencia completa de datos a través de la arquitectura:

  1. PostgreSQL proporcionó los datos maestros y transaccionales de clientes.
  2. Debezium CDC capturó los cambios de la base de datos fila por fila y los publicó en Kafka.
  3. Confluent Cloud transportó y almacenó los eventos en tópicos seguros y particionados.
  4. Schema Registry gobernó el contrato de datos mediante el esquema Avro de las solicitudes.
  5. Flink SQL mantuvo estadísticas acumuladas en streaming y ejecutó un temporal join al milisegundo.
  6. El motor de reglas evaluó la puntuación y escribió la decisión en el tópico loan-decisions.
  7. El Dashboard consumió las decisiones y actualizó los indicadores operacionales en tiempo real.
  8. Terraform y Make permitieron aprovisionar, ejecutar y gobernar toda esta arquitectura con reproducibilidad absoluta.

18. Limpieza de recursos

Al concluir las pruebas del laboratorio, eliminá todos los recursos creados para evitar costes innecesarios:

Terminal
# 1. Detener el tráfico de demo si sigue activo
make demo-traffic-stop

# 2. Destruir los contenedores locales y TODOS los recursos de Confluent Cloud
make destroy
Importante: Control de costes en la nube

El comando make destroy ejecuta scripts/down.sh all, que baja los contenedores locales, elimina los volúmenes de datos, destruye las sentencias de Flink y ejecuta terraform destroy para desaprovisionar el clúster Kafka, Schema Registry, service accounts y entorno en Confluent Cloud.

19. Conclusiones clave

  • UI e IaC son complementarios: La interfaz gráfica de Confluent es excelente para exploración y prototipado rápido, mientras que IaC (Terraform) es el estándar indispensable para entornos productivos reproducibles y auditables.
  • CDC conecta sistemas legados: Debezium y Kafka Connect permiten incorporar bases de datos relacionales al ecosistema de streaming en tiempo real sin modificar aplicaciones existentes.
  • Temporal Joins con Flink SQL: Flink permite enriquecer flujos transaccionales de alta velocidad con tablas maestras cambiantes respetando el estado exacto en el tiempo del evento.
  • Canal unificado: La misma arquitectura procesa de forma transparente tanto solicitudes manuales originadas desde la web como ráfagas continuas de sistemas automáticos.
  • Ciclo de vida gobernado: El aprovisionamiento y destrucción total de la infraestructura se realiza en minutos mediante comandos estándar y código versionado.
