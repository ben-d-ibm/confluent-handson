Banking Real-Time Loan Decisions with Confluent

Building an end-to-end streaming architecture with Infrastructure as Code
"From clicking resources into existence to deploying a reproducible streaming architecture."
01

Introduction

In the previous hands-on laboratory, you explored Confluent Cloud primarily through the web user interface (UI) — manually provisioning clusters, creating topics, registering schemas, and querying stream data.

In this second laboratory, we change paradigms. In enterprise production environments, manual console clicks introduce human error, lack audit trails, and cannot be recreated automatically in CI/CD pipelines.

Here, you will deploy a complete, production-grade real-time loan decision streaming pipeline using Infrastructure as Code (IaC) and end-to-end automation.

💡
The Core Shift Instead of manually configuring dozens of cloud and local settings, you will execute structured automation (make check, make up, make demo-traffic) backed by Terraform, Docker/Podman Compose, and Flink SQL.
02

What are we building?

We are addressing a real-world commercial banking use case: automated, instant loan decisioning.

When a retail customer applies for a loan, traditional batch systems take hours or days to evaluate risk. In a modern event-driven architecture, the bank must correlate multiple disparate signals in sub-second time:

  • Current Loan Request: Amount requested, term in months, purpose, timestamp.
  • Customer Master Profile: Monthly income, current debt, employment stability, customer segment.
  • Historical Payment Behavior: Number of on-time payments, late payments, and historical defaults.

The streaming engine correlates these data streams in real time using temporal joins and applies a multi-variable scoring model (RULES_V1, scale 0–100 points) to emit either an APPROVED or REJECTED decision with full audit reasons.

Evaluation Factor Rule Metric Scoring Impact (Max 100 pts)
Debt-to-Income (DTI) (debt + installment) / income DTI ≤ 30%: 40 pts • ≤ 40%: 25 pts • ≤ 50%: 10 pts • > 50%: 0 pts
Payment History Defaults & Late payments Any defaults: 0 pts • 0 late: 30 pts • ≤ 2 late: 20 pts • > 2 late: 8 pts
Employment Stability Years in current employment ≥ 5 yrs: 15 pts • ≥ 3 yrs: 10 pts • ≥ 1 yr: 5 pts • < 1 yr: 0 pts
Loan Amount Ratio amount / (income * 12) ≤ 50% annual income: 15 pts • ≤ 100%: 8 pts • > 100%: 0 pts
Approval Criteria Overall threshold APPROVED if Score ≥ 60 AND 0 defaults • REJECTED otherwise

Architecture

The solution bridges relational operational databases, event streaming in Confluent Cloud, stateful stream processing via Apache Flink, and microservices for user interaction and monitoring.

Loan Request Web UI (:8080) --> Manual user submission 2. Demo Traffic Producer --> Automated background streaming (make demo-traffic)

🐘 PostgreSQL

Transactional database hosting customer records and payment history table with full replica identity.

🔄 Debezium CDC

Kafka Connect Debezium connector capturing row-level changes into Kafka topics with Avro serialization.

☁️ Confluent Cloud

Managed Kafka cluster and Schema Registry governing data contracts and secure topic storage.

⚡ Flink SQL

Continuous compute pool executing stream aggregations and temporal joins to generate decisions instantly.

📝 Loan Request UI

Express + React application on port 8080 validating input and publishing Avro events.

📊 Live Dashboard

Express + React dashboard on port 8081 consuming decision streams and rendering KPIs.

04

Infrastructure as Code

The key theme of this workshop is declarative infrastructure. Instead of manually clicking in the web UI, the entire topology is defined in code:

make up │ ├── cloud-up ──> Terraform (terraform/) │ ├── Confluent Environment & Kafka Cluster │ ├── Schema Registry & Avro Schemas │ ├── Topics (loan-requests, customers, payment_history) │ ├── Service Accounts, Role Bindings & Least-Privilege ACLs │ ├── Flink Compute Pool │ └── Output: .env.runtime │ ├── local-up ──> Compose (compose/compose.yaml) │ ├── PostgreSQL (schema + seed data) │ ├── Kafka Connect (Debezium CDC connector registration) │ ├── Frontend Loan Requests (:8080) │ └── Frontend Dashboard (:8081) │ └── flink-up ──> Terraform (terraform-flink/) ├── Primary Key Declarations ├── DDL & DML: customer_payment_stats └── DDL & DML: loan-decisions (RULES_V1 scoring engine)

Why Infrastructure as Code for Streaming?

  • Reproducibility: Deploy an identical, complete streaming stack in any region or cloud account with zero configuration drift.
  • Version Control: Track architectural changes, ACLs, scoring thresholds, and schema updates in Git.
  • Least-Privilege Security: Terraform generates dedicated Service Accounts and narrow ACLs for each microservice automatically.
  • Deterministic Teardown: Clean up all cloud and local resources with a single command (make destroy), avoiding lingering cloud costs.

Prerequisites

The environment verification script (scripts/check.sh) checks for the following tools and settings:

1. Required Local Tools

  • Terraform: CLI v1.x or higher (terraform version).
  • Make: Standard GNU Make (make).
  • Curl & JQ: curl and jq for HTTP calls and JSON processing.
  • OpenSSL: Required by make init to generate random passwords.
  • Container Runtime & Compose: Either Docker (docker + docker compose) or Podman (podman + podman compose / podman-compose).

2. Confluent Cloud Account & Credentials

  • An active Confluent Cloud account.
  • A Cloud Resource Management API Key and Secret (created from Confluent Cloud > Top Right Menu > API Keys > Add API Key > Cloud resource management) with permissions to provision environments and service accounts (OrganizationAdmin).

3. Local Network Ports

Ensure the following local ports on 127.0.0.1 are free:

  • 5432: Local PostgreSQL
  • 8083: Kafka Connect REST API
  • 8080: Loan Request Web UI
  • 8081: Real-Time Decision Dashboard
⚠️
Cloud Cost Notice Deploying clusters and Flink compute pools in Confluent Cloud incurs cloud consumption charges. Always execute make destroy at the end of the lab to deprovision all cloud resources.

Configure credentials

The asset includes an initialization script that securely generates your .env configuration with random database credentials:

bash

This creates .env from .env.example with secure permissions (chmod 600). Now, open .env in your preferred editor:

.env (Configuration) 
# --- Confluent Cloud (OBLIGATORIO) -------------------------------------------
# Cloud API key (NO es una API key de clúster). Créala en:
#   Confluent Cloud > menú superior derecha > API keys > Add API key > Cloud resource management
CONFLUENT_CLOUD_API_KEY="YOUR_CLOUD_API_KEY"
CONFLUENT_CLOUD_API_SECRET="YOUR_CLOUD_API_SECRET"

# Región de AWS donde se despliega todo (clúster Kafka + Flink).
CLOUD_REGION="us-east-1"

# Prefijo para nombrar los recursos creados en Confluent Cloud.
PROJECT_NAME="banking-streaming"

# Capacidad máxima del pool de Flink (CFU).
FLINK_MAX_CFU=5

# --- Entorno local ------------------------------------------------------------
CONTAINER_RUNTIME="auto"
POSTGRES_PORT=5432
CONNECT_PORT=8083

# Generadas automáticamente por make init:
POSTGRES_PASSWORD="[auto-generated]"
CDC_PASSWORD="[auto-generated]"
ℹ️
Understanding .env vs .env.runtime
• .env: Your user inputs (Cloud credentials, desired region, ports).
• .env.runtime: Automatically generated by Terraform during make up. Contains dynamically provisioned endpoints, topic names, and per-service API keys. You never need to edit .env.runtime manually.

Deploy everything

Execute the master deployment command. This single command provisions the cloud environment, builds and runs local containers, configures CDC, and starts Flink streaming SQL:

bash 
make up

Deployment Progression

1. [cloud-up] Terraform applies Confluent Cloud resources (~45-60s) --> Environment, Kafka Cluster, Schema Registry, Topics, Flink Pool --> Generates .env.runtime with microservice credentials 2. [local-up] Builds & starts container services via Compose (~15-30s) --> postgres, connect, frontend-requests (:8080), frontend-dashboard (:8081) --> Registers Debezium PostgreSQL connector & waits for RUNNING state 3. [flink-up] Deploys Flink SQL statements via Terraform (~15-20s) --> Configures Primary Keys --> Starts dml-customer-payment-stats (continuous aggregation) --> Starts dml-loan-decisions (temporal join & scoring)
⏱️
Deployment Duration The complete end-to-end deployment typically takes between 1 and 2 minutes depending on network speed and cloud provisioning times.

Open the applications

Open two browser tabs side-by-side to interact with the system:

📝 Loan Request UI

http://127.0.0.1:8080

Origination form. Submits loan applications into the loan-requests Kafka topic. It does not calculate scores.

📊 Real-Time Dashboard

http://127.0.0.1:8081

Operational monitoring. Consumes loan-decisions from Kafka and displays live KPIs, charts, and decisions.

ℹ️
Separation of Concerns & Processing Latency
• Origination UI (:8080): Only validates the form and confirms event submission (202 Accepted). It does not wait for, evaluate, or display loan decisions.
• Decision Pipeline: Flink SQL computes decisions asynchronously and writes them to the loan-decisions topic. In final testing, decisions typically emerge in approximately 5–10 seconds.
• Idle Partitions Configuration: This responsive latency is enabled by setting sql.tables.scan.idle-timeout = '5 s' on the dml-loan-decisions Flink statement, ensuring that temporarily idle topic partitions do not stall the temporal join watermark. (Exact latency may vary slightly depending on cloud network conditions).
• Live Dashboard (:8081): Displays the resulting decision and updates KPIs in real time as events arrive from Confluent Cloud.

Generate continuous traffic

To simulate realistic banking activity across multiple branches and mobile apps, start the background traffic producer:

bash 
make demo-traffic

What this producer does:

  • Runs containerized producer-java in continuous mode in the background.
  • Generates 1 valid loan request every 10 seconds (~6 requests/minute) across customers 1001 to 1050.
  • Generates unique request_id UUIDs and serializes payloads according to the registered Avro schema.

When you wish to stop the traffic generator:

bash 
make demo-traffic-stop

What just happened?

Let us trace the complete path of an event through our automated architecture:

  1. Relational Baseline: PostgreSQL holds customer master data and historical payment logs.
  2. Change Data Capture: Debezium streams every row change into Confluent Cloud topics (customers, payment_history).
  3. Event Origination: A loan application is submitted via Web UI or Java Producer and written to loan-requests.
  4. Contract Governance: Schema Registry validates the message against the loan-requests-value Avro schema.
  5. Continuous Aggregation: Flink SQL maintains up-to-date aggregates of historical payments per customer.
  6. Temporal Join & Scoring: Flink performs a temporal point-in-time join between the request, customer profile, and payment stats, executing the RULES_V1 scoring engine.
  7. Decision Output: Flink writes the result to loan-decisions in Confluent Cloud.
  8. Real-Time Consumption: The React dashboard displays the resulting decision and updates portfolio KPIs.
  9. Declarative Orchestration: Terraform and Make provisioned and orchestrated this entire multi-tier system reproducibly in minutes.

Clean up

When you have completed the laboratory, clean up all provisioned resources:

bash 
# 1. Stop background traffic (if running)
make demo-traffic-stop

# 2. Teardown all local containers and delete all Confluent Cloud resources
make destroy
🚨
Important: Avoid Unintended Cloud Costs Running make destroy executes scripts/down.sh all, which stops and removes local containers, drops local volumes, tears down Flink SQL statements, and runs terraform destroy to remove the Kafka cluster, Schema Registry, service accounts, and environment in Confluent Cloud.

Key takeaways

  • UI and IaC are Complementary: The Confluent Cloud UI is ideal for visual exploration, while Terraform provides automated, version-controlled, auditable deployments.
  • CDC Unlocks Legacy Databases: Debezium and Kafka Connect continuously stream operational data into Confluent without rewriting legacy applications.
  • Temporal Joins in Flink: Flink SQL enables joining high-velocity transaction streams with changing reference tables as of the exact event time.
  • Single Pipeline, Diverse Traffic: The same governed streaming architecture transparently supports manual web submissions and high-throughput automated producers.
  • Deterministic Environments: With Make, Compose, and Terraform, spinning up and tearing down sophisticated event-driven applications is completely automated.
