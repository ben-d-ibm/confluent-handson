# Spike 1.1 — CDC (PostgreSQL → Debezium) → Confluent Cloud → Flink SQL

Resultado: **la integración funciona**. Un `UPDATE` en `customers` y un `INSERT` en `payment_history` llegan a Flink, cambian el estado vigente y una nueva solicitud usa los valores actualizados. Hay un requisito obligatorio (`REPLICA IDENTITY FULL`) y tres limitaciones a tener en cuenta (sección 9).

## 1. Arquitectura validada

```
PostgreSQL 18 (wal_level=logical, REPLICA IDENTITY FULL)
  └─ Debezium 3.7.0 (Kafka Connect 4.4.0, AvroConverter 8.4.0)  ──►  tópicos `customers`, `payment_history`
                                                                          │  (Avro + Schema Registry, envelope Debezium completo)
loan-requests (Avro) ───────────────────────────────────────────────────┐ │
                                                                         ▼ ▼
                    Flink SQL:  customer_payment_stats  (GROUP BY customer_id, upsert)
                                loan-requests ⟕ customers (temporal join) ⟕ customer_payment_stats (temporal join)
```

## 2. Formato Debezium y Schema Registry
- El conector publica el **envelope completo** (`before`, `after`, `source`, `op`, `ts_ms`…), sin `ExtractNewRecordState`. Flink lo interpreta de forma nativa.
- Converters: `io.confluent.connect.avro.AvroConverter` en clave y valor, con Schema Registry de Confluent Cloud (`USER_INFO`).
- Flink infiere solo la tabla: `value.format = avro-debezium-registry`, `key.format = avro-registry`. **No hace falta `CREATE TABLE`** para los CDC.
- Subjects: `customers-key`, `customers-value`, `payment_history-key`, `payment_history-value` (versión 1).
- El `RegexRouter` (`bank.public.(.*)` → `$1`) deja los tópicos con el nombre de la tabla.

## 3. Keys y PKs
| Tópico | Clave Kafka | PK en Flink |
|---|---|---|
| `customers` | Avro `{customer_id}` | `customer_id` |
| `payment_history` | Avro `{payment_id}` | `payment_id` |
| `loan-requests` | `raw` (bytes, opcional) | no aplica (append) |

Flink **no declara la PK** al inferir la tabla. Hay que añadirla (solo metadatos, `NOT ENFORCED`):
```sql
ALTER TABLE customers       ADD PRIMARY KEY (customer_id) NOT ENFORCED;
ALTER TABLE payment_history ADD PRIMARY KEY (payment_id)  NOT ENFORCED;
```
Sin PK en `customers` no es posible el temporal join. Con ella, `EXPLAIN` muestra `Primary key: (customer_id)` y `Upsert key: (customer_id)`.

## 4. Changelog modes
| Tabla | `changelog.mode` | Notas |
|---|---|---|
| `customers`, `payment_history` | `retract` | `+I` insert, `-U`/`+U` update, `-D` delete |
| `customer_payment_stats` (CTAS) | `upsert` | tópico compactado, PK `customer_id` |
| `loan-requests` | `append` | |

Con PK, el planificador inserta `StreamDropUpdateBefore` y trabaja en modo `upsert` internamente.

## 5. Tipos y conversiones
| Origen (Flink infiere) | Necesidad | Expresión validada |
|---|---|---|
| `payment_history.due_date` `INT` (días desde 1970) | `DATE` | `CAST(TIMESTAMPADD(DAY, due_date, DATE '1970-01-01') AS DATE)` |
| `payment_history.paid_date` `INT` nullable | `DATE` | la misma expresión (propaga `NULL`) |
| `customers.updated_at` `STRING` (`2026-10-30T17:21:43.132352Z`) | `TIMESTAMP(3)` | `CAST(REPLACE(REPLACE(updated_at,'T',' '),'Z','') AS TIMESTAMP(3))` |
| `monthly_income`, `monthly_debt`, `amount` | `DECIMAL(12,2)` | sin conversión (`decimal.handling.mode=precise`) |

- Resultado comprobado: `20423 → 2025-12-01`, `20393 → 2025-11-01`.
- `updated_at` llega como texto porque `timestamptz` va como `ZonedTimestamp` (string ISO-8601). Alternativa aceptable: `TO_TIMESTAMP_LTZ(updated_at, 'yyyy-MM-dd''T''HH:mm:ss.SSSSSS''Z''')`.
- **Falla:** `UNIX_TIMESTAMP(...)` sobre un changelog: *"generated by non-deterministic function: UNIX_TIMESTAMP … can not satisfy the determinism requirement"*. No usarla.
- **Falla:** `DATE_FORMAT(<DATE>, ...)`: solo acepta `TIMESTAMP` o `CHARACTER`.
- El scoring no necesita `updated_at`. Se conserva solo por trazabilidad.

## 6. Estrategia de join (decisión)
1. **`customer_payment_stats`**: agregado por `customer_id` (CTAS con PK) en `01-customer-payment-stats.sql`. Calcula `total_payments`, `late_payments`, `defaulted_payments`, `unpaid_payments` y `last_due_date`.
2. **`loan-requests` ⟕ `customers`** con temporal join `FOR SYSTEM_TIME AS OF l.$rowtime`.
3. **`⟕ customer_payment_stats`** con otro temporal join sobre la tabla materializada.
4. `LEFT JOIN` + `COALESCE(..., 0)` en los contadores para clientes sin historial. Un cliente inexistente (`99999`) produce una fila con campos del cliente `NULL`, y la 1.4 debe decidir qué hacer con ella (propuesta: rechazar con motivo `CUSTOMER_NOT_FOUND`).

Por qué esta opción:
- Un join directo con `payment_history` multiplica cada solicitud por el número de pagos (una fila por pago). Se descarta.
- Un regular join con el agregado reemite decisiones cada vez que cambia el cliente o su historial, ya que el resultado es un changelog. Para una decisión por solicitud eso es incorrecto.
- El temporal join produce **una sola decisión por solicitud, con el valor vigente cuando llega**, y no la reemite después.

**Error encontrado:** un temporal join contra un `WITH pay AS (SELECT ... GROUP BY ...)` (CTE/subconsulta) falla con
`Event-Time Temporal Table Join requires both primary key and row time attribute in versioned table, but no row time attribute can be found.`
Solución: materializar el agregado en una tabla (CTAS con PK) y unirla por temporal join. Con la tabla, `EXPLAIN` da `StreamTemporalJoin` con `Changelog mode: append`. Un `LEFT JOIN` normal contra el CTE también compila (modo `retract`), pero no es lo que queremos.

### Cómo se actualiza el agregado
Cada `INSERT`/`UPDATE`/`DELETE` de `payment_history` produce un cambio en el aggregate de ese cliente: Flink emite `-U` con la fila antigua y `+U` con la nueva, y el tópico compactado `customer_payment_stats` conserva la última por `customer_id`. Un `DELETE` decrementa los contadores. Las solicitudes ya decididas no cambian; solo las nuevas ven el valor actualizado.

## 7. Pruebas reales

### 7.1 UPDATE en `customers` (cliente 1001: `monthly_income` 8000 → 3000 → 3100)
| Comprobación | Resultado |
|---|---|
| Debezium emite el cambio | Sí, un evento `op=u` por cada `UPDATE` |
| Flink recibe `-U`/`+U` | Sí: `{op:1, 3000.00}` y `{op:2, 3100.00}` (lectura desde el offset 17) |
| Estado actual actualizado | Sí, el temporal join devuelve 3100.00 |
| Nueva solicitud usa el valor nuevo | Sí. `spike-base-1` (antes): 8000.00 · `spike-after-1` (después): **3100.00** |

### 7.2 INSERT en `payment_history` (cliente 1001, `DEFAULTED`, `paid_date` NULL)
| Comprobación | Resultado |
|---|---|
| Debezium emite `+I` | Sí: `payment_id=313`, `op:0` |
| Cambia el agregado | Sí: `12/0/0/0` → `13/0/1/1`, `last_due_date` 2025-12-01 → 2026-09-30 |
| Nueva solicitud refleja el historial | Sí: `spike-base-1` `total=12, defaulted=0` · `spike-after-1` `total=13, defaulted=1` |

### 7.3 DELETE (reversión de la prueba)
`DELETE FROM payment_history WHERE payment_id=313` llegó como `-D` (`op:3`) y el agregado volvió a `12/0/0/0`. El `monthly_income` de 1001 se restauró a 8000.

### 7.4 Cliente inexistente
`spike-missing-1` (customer 99999) → `monthly_income = NULL`, contadores a 0.

## 8. Requisito obligatorio: `REPLICA IDENTITY FULL`
Con la identidad por defecto de PostgreSQL, un `UPDATE` llega con `before = null`. Flink no puede leerlo y la sentencia falla con:
`Error while deserializing value from topic 'customers', partition 0, offset 16. Please ensure that the declared value schema matches your records.`
Solución aplicada en `postgres/init/01-schema.sql`:
```sql
ALTER TABLE customers       REPLICA IDENTITY FULL;
ALTER TABLE payment_history REPLICA IDENTITY FULL;
```
Los entornos nuevos nacen con esto. En el entorno de pruebas ya se aplicó en caliente.

## 9. Limitaciones y riesgos residuales
1. **Registro "envenenado": RESUELTO.** Un `UPDATE` hecho antes de activar `REPLICA IDENTITY FULL` (offset 16, partición 0 de `customers`) impedía leer `customers` desde `earliest-offset`. Se recuperó el entorno con el procedimiento de la sección 14 y `make flink-check` está en OK. Si vuelve a ocurrir, repetir ese procedimiento.
2. **Opciones de hint admitidas** en tablas Confluent: `scan.startup.mode`, `scan.startup.specific-offsets`, `scan.startup.timestamp-millis`, `scan.bounded.mode`, `scan.bounded.specific-offsets`, `scan.bounded.timestamp-millis`, `kafka.consumer.isolation-level`, `kafka.producer.compression.type`. `error-handling.mode` **no** se admite como hint.
3. **`LIMIT` no acota** la consulta sobre un tópico: la sentencia sigue `RUNNING` (no es *bounded*). Usa `scan.bounded.mode='latest-offset'` o `--max-rows`.
4. **Temporal join y watermarks.** Las tablas usan `SOURCE_WATERMARK()`. La salida del temporal join depende del watermark de la tabla versionada, así que con poco tráfico puede tardar (observado: ~25 s). El smoke test debe esperar con timeout.
5. **Valores "vigentes" por tiempo de evento.** Una solicitud usa la versión del cliente cuyo `$rowtime` es ≤ al suyo. Si un `UPDATE` llega con `$rowtime` posterior al de la solicitud, no se aplica, y una solicitud muy antigua puede usar datos antiguos (aceptable).
6. **Cálculo de `last_due_date` y fechas futuras:** `due_date` puede ser posterior a hoy; la regla de "vencido" debe comparar contra `CURRENT_DATE`.
7. **Tipos:** `updated_at` como texto y fechas como `INT` (sección 5) son consecuencia de la configuración de Debezium (`time.precision.mode=adaptive`). Alternativa para la 1.3: `time.precision.mode=connect` daría tipos lógicos de Avro; no se ha probado.

## 10. Decisión final para la Fase 1.4
- Tablas CDC inferidas por Flink + PK declarada por `ALTER TABLE` (script de inicialización).
- `customer_payment_stats` (CTAS, tópico compactado) mantiene el agregado de pagos por cliente.
- Enriquecimiento con **dos temporal joins** `LEFT JOIN … FOR SYSTEM_TIME AS OF l.$rowtime`.
- Conversión de fechas con la expresión de la sección 5. No usar `UNIX_TIMESTAMP`.
- Una sola decisión por solicitud, sin reemisión por cambios posteriores del cliente o del historial.
- Cliente inexistente: decisión `REJECTED` con motivo `CUSTOMER_NOT_FOUND` (a implementar en 1.4).
- Los statements permanentes (CTAS de stats e INSERT de decisiones) se desplegarán con `confluent_flink_statement` en Terraform, no con el script ad hoc.
- Orden de creación: PKs → `customer_payment_stats` → INSERT de decisiones.
- La 1.4 está implementada: ver `README.md` (tabla `loan-decisions`, reglas, umbrales en `var.scoring`).

## 11. Comandos seguros para diagnóstico
Todos con plazo finito. Se ejecutan con `bash scripts/flink-sql.sh` (bash, no `source` desde zsh).

```bash
make flink-check                                         # salud + conteos acotados
bash scripts/flink-sql.sh --timeout 40 "SHOW TABLES"
bash scripts/flink-sql.sh --timeout 40 "SHOW CREATE TABLE customers"
bash scripts/flink-sql.sh --timeout 60 --max-rows 20 \
  "SELECT * FROM customers /*+ OPTIONS('scan.bounded.mode'='latest-offset') */ WHERE customer_id = 1001"
# Conteo acotado (NO usar COUNT(*) sin acotar como health check)
bash scripts/flink-sql.sh --timeout 60 --max-rows 20000 \
  "SELECT COUNT(*) FROM payment_history /*+ OPTIONS('scan.bounded.mode'='latest-offset') */"
# Ver cambios (-U/+U) desde un offset concreto
bash scripts/flink-sql.sh --timeout 90 --max-rows 20 "SELECT customer_id, monthly_income FROM customers
  /*+ OPTIONS('scan.startup.mode'='specific-offsets','scan.startup.specific-offsets'='partition:0,offset:17;partition:1,offset:0;partition:2,offset:0','scan.bounded.mode'='latest-offset') */
  WHERE customer_id = 1001"
# EXPLAIN (no ejecuta nada)
bash scripts/flink-sql.sh --timeout 60 -f consulta.sql     # con la consulta precedida de EXPLAIN
```
Interpretación de `op`: `0` = `+I`, `1` = `-U`, `2` = `+U`, `3` = `-D`. La salida de una agregación incluye el changelog completo: el valor final es el último `+I`/`+U`.

## 12. Cómo evitar statements Flink huérfanos
- `flink-sql.sh` borra su sentencia al salir (`trap EXIT/INT/TERM/PIPE`) y tiene plazo global. No usar `--no-wait` salvo para statements continuos **intencionados**; devuelven el nombre para poder pararlos.
- Un `SELECT` sin acotar queda `RUNNING` y consume CFU mientras exista. Siempre acotar o usar `--max-rows`.
- Listar y limpiar:
```bash
bash -c 'source scripts/lib.sh; load_env; set -a; source .env.runtime; set +a
BASE="${FLINK_REST_ENDPOINT}/sql/v1/organizations/${CONFLUENT_ORG_ID}/environments/${CONFLUENT_ENV_ID}"
curl -sS --max-time 20 -K <(printf "user = \"%s\"\n" "${FLINK_API_KEY}:${FLINK_API_SECRET}") "${BASE}/statements?page_size=50" \
  | jq -r ".data[] | [.name,.status.phase] | @tsv"'
# Borrar uno: curl ... -X DELETE "${BASE}/statements/<nombre>"
```
- Borrar el statement de un CTAS **detiene** el flujo que alimenta la tabla; la tabla queda pero deja de actualizarse.
- Para pruebas con efectos, usar nombres con prefijo `spike-`/`adhoc-` y limpiar al final. En este spike se borraron `spike_enriched` y `customer_payment_stats`.

## 14. Recuperación de un entorno CDC contaminado (procedimiento aplicado)
Úsalo si un tópico CDC contiene registros ilegibles para Flink (p. ej. `UPDATE` anterior a `REPLICA IDENTITY FULL`). **No toca** la infraestructura base (entorno, clúster, Schema Registry, cuentas de servicio, API keys, compute pool) ni los tópicos internos de Connect (`config/offsets/status`).

1. Verificar `REPLICA IDENTITY FULL` (`relreplident = 'f'`) en ambas tablas y en `postgres/init/01-schema.sql`.
2. Parar el conector: `PUT /connectors/banking-postgres-cdc/stop` (el slot queda inactivo).
3. Recrear solo los tópicos de las dos tablas con Terraform y un plan guardado:
   `terraform plan -replace=confluent_kafka_topic.customers -replace=confluent_kafka_topic.payment_history -out=…` y `terraform apply` de ese plan (2 destruidos, 2 creados; nada más).
4. Borrar los offsets de este conector: `DELETE /connectors/banking-postgres-cdc/offsets` (solo funciona con el conector parado).
5. Eliminar el slot inactivo: `SELECT pg_drop_replication_slot('banking_slot')`. Sin esto Debezium reanudaría desde el LSN antiguo y no haría snapshot.
6. Reanudar: `PUT /connectors/banking-postgres-cdc/resume`. Debezium recrea el slot y hace un snapshot completo (exportó 50 `customers` y 312 `payment_history`).
7. Reaplicar las PKs en Flink: `bash scripts/flink-sql.sh -f flink-sql/00-primary-keys.sql` (o sentencia a sentencia).
8. Validar: `make flink-check` y `terraform plan -detailed-exitcode` (sin drift).

Notas del caso real:
- **Schema Registry:** el borrado de los subjects `customers-*` y `payment_history-*` fue denegado (error 40301, la API key no tiene `Delete`). Se mantuvieron en versión 1; el esquema Debezium es idéntico, así que el nuevo snapshot los reutiliza sin problema. No es necesario borrarlos.
- `GET …/offsets` devuelve vacío tras reanudar hasta que se confirma el primer evento de streaming; es normal.
- Resultado final: `flink-check` OK (50 y 312 filas leídas desde el principio), sin statements huérfanos, sin drift de Terraform.
